# 测绘地理信息数据安全平台项目架构

## 1. 架构目标

本系统采用“两台核心服务器 + 多台内网终端”的部署方式。

- 服务器1：接收终端上传的数据和处理请求，作为数据接入服务器。
- 服务器2：执行隔离计算、水印处理、审计存证，并向终端提供授权后的处理结果，作为数据处理与结果输出服务器。
- 终端电脑：只能按照授权方向访问服务器，不允许直接访问数据库、加密卷、原始数据目录或内部处理程序。
- 终端数量：当前支持2台测试终端，生产环境预留至少11台终端，可继续扩展。

核心原则：

```text
终端上传数据/提交请求       → 服务器1（唯一接收入口）
服务器1转交数据和任务       → 服务器2
服务器2完成沙箱计算和水印   → 服务器2
服务器2输出审核通过的结果   → 终端（唯一结果出口）
```

这里的“只能访问”指业务权限和接口方向，不是指网络层面只能看到一台服务器：

- 终端对服务器1只开放数据接收和业务请求接口；
- 终端对服务器2只开放授权结果输出接口；
- 终端不能用服务器2上传原始数据；
- 终端不能从服务器1读取服务器2的原始数据；
- 两台服务器之间通过内部服务接口传递数据、任务状态和审计信息；
- 终端不能直接访问数据库、加密卷、文件共享、沙箱和区块链管理接口。

原始数据和处理过程不直接暴露给终端。

## 2. 推荐的设备角色

### 服务器1：数据接入服务器

服务器1是终端上传数据和提交处理请求的入口。

主要职责：

- 接收终端上传的数据；
- 接收数据导入、处理和导出请求；
- 用户登录和身份认证；
- 用户、角色和项目权限管理；
- 检查上传数据的项目归属和格式；
- 生成文件ID、项目ID和任务ID；
- 对上传文件进行基础病毒检查、哈希计算和完整性检查；
- 将经过校验的数据和任务请求提交给服务器2；
- 保存文件索引、任务状态和业务记录；
- 向终端返回上传状态和任务进度。

服务器1不直接承担大型水印计算，不向终端暴露服务器2的内部目录。

服务器1原则上不保存长期原始数据。上传文件可以先进入受控的临时接收区，校验通过后转入服务器2的项目加密空间，并在传输确认后清理临时文件。

### 服务器2：隔离计算和结果输出服务器

服务器2是数据安全处理核心，也是唯一的终端结果输出服务器。

主要职责：

- 只接收服务器1转交的已授权数据和任务，不接收终端原始数据上传；
- 挂载项目专属 VeraCrypt 加密卷；
- 按项目创建产品运行空间和产品研发空间；
- 在 AppContainer Sandbox-Plus 或等效受控环境中执行任务；
- 调用安全计算引擎、PostGIS、文件库和算法库；
- 执行GDAL脱敏、精度降低和格式处理；
- 执行GeoTIFF、SHP/GeoJSON、DLG、OSGB水印处理；
- 执行任务完成后的结果审核；
- 保存处理结果和授权输出文件；
- 只向终端提供审核通过的结果下载、在线地图/模型服务和追溯查询；
- 记录Sysmon主机行为日志；
- 写入Elasticsearch审计日志；
- 触发ElastAlert2异常告警；
- 将关键归属和流转记录写入FISCO BCOS；
- 生成水印证据、链上查询结果和追溯报告。

服务器2不接受终端的原始数据上传和任意管理访问。终端只能访问服务器2上经过授权的结果输出接口，不能访问服务器2的数据库、文件共享、管理端口和原始数据目录。

### 终端电脑：业务操作终端

生产环境至少预留11台终端。

终端通过浏览器或安全客户端完成：

- 登录系统；
- 上传数据；
- 创建和查看项目；
- 提交处理任务；
- 查看任务进度；
- 查看审核状态；
- 下载授权结果；
- 查询审计记录和流转凭证；
- 按权限使用GeoServer在线服务；
- 可选的OSGB三维预览。

终端不安装：

- PostgreSQL/PostGIS；
- Elasticsearch；
- FISCO BCOS；
- VeraCrypt项目卷；
- 水印处理程序；
- 沙箱管理程序。

## 3. 推荐网络架构

### 3.1 生产环境：内网交换机连接

生产环境采用内网物理接入。至少11台终端、服务器1和服务器2接入甲方内网交换机；如果甲方要求终端区和服务器区隔离，则分别划分VLAN并通过防火墙放行业务接口。

```text
终端1...终端11
      │
      ▼
  内网交换机
   ├──────── 服务器1：唯一数据接收入口
   │            （终端上传、请求、状态查询）
   │
   └──────── 服务器2：唯一结果输出入口
                （授权下载、在线服务、追溯查询）

服务器1 ──────── 服务器2
       内部受控服务链路
```

生产环境中的访问方向必须固定：

- 终端到服务器1：只开放登录、数据上传、项目操作、任务提交和状态查询；
- 终端到服务器2：只开放审核通过结果的下载、在线地图/模型服务和追溯查询；
- 终端不能通过服务器2上传原始数据；
- 终端不能通过服务器1读取服务器2的原始数据；
- 服务器1到服务器2：只开放数据转交、任务提交、状态回传和必要的审计接口；
- 数据库、Elasticsearch、FISCO BCOS、VeraCrypt和沙箱管理端口不对终端开放。

如果甲方要求服务器区和终端区隔离，则在终端区与服务器区之间增加防火墙，按上述接口方向配置白名单。

### 3.2 推荐的生产安全分区

```text
┌─────────────────────────────────────────────┐
│                 生产内网                     │
│                                             │
│  ┌──────────────┐       ┌──────────────┐   │
│  │ 终端区 VLAN   │──────▶│ 应用访问防火墙 │   │
│  │ 至少11台终端  │       └──────┬───────┘   │
│  └──────────────┘              │           │
│                         ┌──────▼───────┐   │
│                         │ 服务器1       │   │
│                         │ 接入/API      │   │
│                         └──────┬───────┘   │
│                                │           │
│                         ┌──────▼───────┐   │
│                         │ 服务器2       │   │
│                         │ 处理/输出     │   │
│                         └──────────────┘   │
└─────────────────────────────────────────────┘
```

如果甲方不要求细分VLAN，可以先使用一个受控内网；软件本身仍然按服务器1、服务器2和终端三类访问权限实施，后续可以迁移到VLAN和防火墙架构。

## 4. 终端访问控制模型

终端不是“可以访问服务器1和服务器2的全部服务”，而是按接口方向限制。

| 来源 | 目标 | 允许内容 | 禁止内容 |
|---|---|---|---|
| 终端 | 服务器1 | 登录、上传、项目操作、提交任务、查询状态 | 数据库、系统管理、服务器文件目录 |
| 终端 | 服务器2 | 授权结果下载、在线地图/模型服务、追溯查询 | 原始数据、加密卷、数据库、沙箱、管理接口 |
| 服务器1 | 服务器2 | 文件转交、任务提交、状态查询、结果索引、审计事件 | 不必要的系统级访问 |
| 服务器2 | 服务器1 | 结果状态、任务状态、链上凭证和处理结果通知 | 反向开放管理权限 |
| 运维终端 | 服务器1/2 | 经过堡垒机或安全容器的运维操作 | 普通业务终端直接运维 |

服务器2对终端提供的是“输出接口”，不是文件共享目录。结果下载必须经过：

```text
用户认证 → 项目权限 → 结果审核 → JWT/授权令牌 → 结果输出 → 审计记录
```

## 5. 推荐业务数据流

### 5.1 数据导入流程

```text
终端
  │ 上传数据、填写项目和数据说明
  ▼
服务器1：接入/API
  │ 身份、项目权限、格式、哈希、大小检查
  ▼
服务器1：生成项目ID、文件ID、任务ID
  │ 受控传输，不让终端直接写服务器2目录
  ▼
服务器2：挂载项目专属VeraCrypt卷
  │ 写入项目加密空间
  ▼
服务器2：保存原始数据
  │ 返回接收结果和文件索引
  ▼
服务器1：更新任务状态和元数据
  │ 记录审计并返回终端
  ▼
终端：看到导入成功
```

### 5.2 处理和水印流程

```text
终端提交任务
       ▼
服务器1检查权限并创建任务
       ▼
服务器2创建项目运行空间
       ▼
挂载VeraCrypt项目加密卷
       ▼
AppContainer Sandbox-Plus受控执行
       ▼
安全计算、GDAL脱敏/精度降低
       ▼
GeoTIFF/SHP/DLG/OSGB水印处理
       ▼
人工或自动审核
       ▼
生成授权输出文件
       ▼
卸载VeraCrypt加密卷
```

### 5.3 结果输出流程

```text
终端请求结果
       ▼
服务器2验证结果状态和输出权限
       ▼
服务器1或服务器2生成一次性授权令牌
       ▼
服务器2只输出审核通过的结果
       ▼
终端下载或通过GeoServer受控访问
       ▼
Elasticsearch记录输出日志
       ▼
FISCO BCOS记录关键流转凭证
```

这里的设计重点是：服务器2可以向终端输出结果，但不能让终端通过输出接口反向列举、读取或下载原始项目数据。

## 6. 测试环境和生产环境的区别

### 6.1 当前测试环境

当前测试环境允许两台电脑远程连接两台服务器，适合开发和联调：

```text
测试电脑1 ──远程连接──┐
                       ├── 服务器1
测试电脑2 ──远程连接──┘
                       └── 服务器2
```

测试阶段可以临时允许：

- 远程桌面或远程管理；
- 开发人员访问服务器日志；
- 开发人员直接查看服务状态；
- 两台测试电脑模拟终端上传和结果下载。

但测试远程连接不应写进生产业务逻辑。生产系统必须将：

- 业务访问；
- 管理访问；
- 数据输出；
- 服务间通信；

分开控制。

### 6.2 生产环境

生产环境使用内网连接：

```text
终端1...终端11
        │
        ▼
     内网交换机
       ├────────服务器1：接收数据/请求
       └────────服务器2：处理数据/输出结果
```

软件必须通过配置文件区分测试和生产：

```text
环境配置：test / production
服务器1地址：配置项
服务器2地址：配置项
终端访问入口：配置项
结果输出地址：配置项
数据库地址：仅服务器端配置
服务端口：配置项
TLS证书路径：配置项
```

不能把测试阶段的远程桌面地址、临时IP或开发端口写死到程序中。

## 8. 服务器2向终端输出的方式

本项目正式采用“服务器1接收、服务器2输出”的双入口模型：

```text
终端 ──上传/提交请求──▶ 服务器1
终端 ──授权结果获取──▶ 服务器2
服务器1 ──内部转交/任务控制──▶ 服务器2
```

这意味着终端可以访问两台服务器，但每台服务器的业务接口和权限完全不同：

- 服务器1不是结果文件服务器；
- 服务器2不是原始数据接收服务器；
- 终端不能通过服务器2上传原始数据；
- 终端不能通过服务器1读取服务器2的原始数据；
- 服务器2只输出审核通过且与当前用户、项目、任务绑定的结果。

结果输出必须经过：

```text
终端登录态/令牌
→ 项目权限校验
→ 结果审核状态校验
→ 一次性或短时授权令牌
→ 服务器2结果接口
→ 下载/在线服务
→ 审计和链上登记
```

### 服务器2结果接口的边界

服务器2对终端只开放：

- 审核通过的结果下载；
- 授权的GeoServer地图服务；
- 授权的OSGB/模型预览服务；
- 追溯查询和报告下载。

服务器2不对终端开放：

- 原始数据上传；
- 原始数据目录浏览；
- VeraCrypt盘符访问；
- PostgreSQL/PostGIS端口；
- Elasticsearch/Kibana管理接口；
- FISCO BCOS节点管理接口；
- 沙箱管理接口；
- Windows远程管理端口。

采用这种方式可以避免10GB级结果经过服务器1中转，同时保持服务器2只承担“处理后结果输出”的职责。

如果甲方后续要求终端实际上只能访问一个IP入口，则可以在服务器1增加结果反向代理，但这属于网络入口变化，服务器2的业务职责不变。

## 9. 推荐最终架构结论

### 推荐主方案：单入口、双服务器内部协作

```text
┌──────────────┐
│ 终端1...终端11 │
└──────┬───────┘
       │ 仅访问统一平台入口
       ▼
┌────────────────────┐
│ 服务器1             │
│ 唯一终端访问入口     │
│ 接入、权限、任务、输出代理│
└─────────┬──────────┘
          │ 内部受控通信
          ▼
┌────────────────────┐
│ 服务器2             │
│ 加密存储、沙箱、计算  │
│ 四类水印、审计、区块链 │
│ 结果输出服务          │
└────────────────────┘
```

这套方案同时满足：

- 终端只访问一台服务器；
- 服务器1负责接收数据；
- 服务器2负责处理数据和生成结果；
- 服务器2的结果可以通过服务器1安全输出给终端；
- 测试环境可使用远程连接；
- 生产环境可通过内网交换机连接；
- 可预留至少11台终端；
- 不需要改变核心业务代码即可切换网络地址和部署环境。

## 10. 开始写代码前必须冻结的架构决定

1. 是否采用“终端唯一访问服务器1”的主方案；
2. 如果服务器2直接向终端输出，服务器2只开放哪些结果接口；
3. 服务器1到服务器2的通信方式；
4. 测试环境IP和生产环境IP是否通过配置文件切换；
5. 终端数量上限是否按至少11台设计；
6. 内网是否使用一个交换网段，还是终端区/服务器区VLAN；
7. 生产环境是否允许HTTPS/TLS；
8. 服务器2的1TB磁盘如何分配原始数据、处理结果、临时文件和日志；
9. 服务器2是否同时承载GeoServer结果服务；
10. FISCO BCOS的4个逻辑节点如何在两台服务器上部署。

在这些决定完成后，代码可以先从以下部分开始：

```text
配置文件
→ 服务器1/服务器2服务骨架
→ 终端登录和上传
→ 服务器1到服务器2的内部任务协议
→ 结果输出接口
→ 统一审计事件
```
